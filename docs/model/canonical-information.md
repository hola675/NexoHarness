# NexoHarness Canonical Information

Status: ACTIVE. This document is the organizational/system information model for NexoHarness: what information exists, where it belongs, what authority it carries, how it may flow between layers, what may become canonical, and what may never be treated as canonical input.

**A schema can be canonical while the data it validates remains runtime, research, generated or validation evidence.** Information carries authority through its class, root and governance, never through the shape used to validate it.

It builds on, and does not replace or modify:

```text
docs/source-of-truth.md                       (technical owner: directory ownership, class definitions)
docs/canonical-format.md                      (technical owner: manifest envelope)
docs/schema-system.md                         (technical owner: schemas and registry)
docs/validation.md                            (technical owner: validation pipeline)
docs/decisions/0001-canonical-manifest-model.md
core/schemas/registry.json
core/schemas/common.schema.json
core/schemas/observation.schema.json
core/schemas/improvement-proposal.schema.json
core/schemas/evaluation.schema.json
core/schemas/contract.schema.json
core/policies/self-improvement.md
tools/validate/canonical-discovery.ts
tools/validate/canonical-integrity.ts
tools/validate/references.ts
tools/validate/repository.ts
```

**Nothing here changes implementation.** No schema, registry entry, canonical root, validator, adapter, Observer runtime or runtime-reference resolver is added or modified. The counts below (13 registered Kinds, 11 canonical authoring roots) describe the current technical state, verified against code. They are facts about today, not permanent invariants.

## Shape is not authority

```text
REGISTERED KIND != CANONICAL AUTHORED INSTANCE
SCHEMA DEFINITION != INFORMATION INSTANCE
```

- A **schema** is the canonical definition of a valid information shape.
- An **instance** is information that carries its own information class, independent of the class of the schema that validates it.

`core/schemas/observation.schema.json` is CANONICAL: it is part of the governed definition of NexoHarness. An Observation record validated by it is RUNTIME evidence. A canonical schema for a type of information does not make every instance of that type canonical behavior.

## Information classes

NexoHarness recognizes exactly five information classes. No further top-level class is introduced; finer distinctions are descriptive categories inside a class.

| Class | Definition |
|---|---|
| **CANONICAL** | Authored source that defines intended, governed NexoHarness semantics, behavior, constraints or assurance expectations. |
| **RUNTIME** | Information representing actual execution state, operational evidence or non-canonical operational artifacts. |
| **RESEARCH** | Investigation or external evidence used to understand targets, technologies, prior art or design options. |
| **GENERATED** | Deterministic or controlled derived output produced from source definitions for a target or distribution. |
| **VALIDATION** | Information whose primary purpose is to test, evaluate, verify or certify claims about another artifact or behavior. |

| Class | Defines intended behavior? | Operational / current? | May be authored manually? | May directly drive canonical behavior? |
|---|---|---|---|---|
| CANONICAL | Yes | No, by definition | Yes | Yes, within its authority |
| RUNTIME | No | Yes | Sometimes | No |
| RESEARCH | No | No (it may record evidence that was current when observed) | Yes | No |
| GENERATED | Derived only | No | No manual authoring | No |
| VALIDATION | No | Sometimes | Yes, or generated by tooling | No |

### CANONICAL

Conceptually includes Directives, Policies, canonical entity definitions, schemas, canonical Evaluation Definitions, and approved adapter implementation source where applicable. Two descriptive categories (not additional classes) keep it precise:

- **Semantic canonical source:** material that defines what NexoHarness means independently of any harness: `core/directives/`, `core/policies/`, `core/contracts/`, `core/schemas/`, `agents/`, `skills/`, `rules/`, `workflows/`, `capabilities/`, `profiles/`, `enforcement/` and `evals/`, when they contain real entities. Today only `core/directives/` (2 Directives), `core/policies/` (6 Policies) and `core/schemas/` hold content; every other canonical root holds only `.gitkeep`.
- **Target implementation source:** `adapters/` is the source-controlled, authoritative *implementation* of the translation boundary for one target. It is authoritative for, for example, Codex translation behavior, and it remains target-specific.

```text
CANONICAL != NECESSARILY HARNESS-NEUTRAL
ADAPTER CODE != HARNESS-NEUTRAL CANONICAL SEMANTICS
```

Neutrality is required wherever the architecture requires it: in semantic canonical source, not in every CANONICAL artifact. Adapter implementation can never redefine the canonical model (`docs/source-of-truth.md`, ownership rule 2).

**Canonical does not grant arbitrary authority.** A CANONICAL artifact defines intended semantics within its scope. That does not make it a source of Authority. An Agent's dimensional `authority` describes bounds that may be authorized; a Capability names a need; a Skill explains a procedure. Authority semantics continue to follow Governance ([`governance-authority.md`](governance-authority.md), `core/policies/*`).

### RUNTIME

Conceptually includes, according to each artifact's lifecycle: Assignment state, Work Unit state, Contract Instances, Observation instances, Runtime Snapshots, Effective Configuration, current provider state, runtime diagnostics and ImprovementProposal instances. None of these is persisted by an implementation today. `observer/` holds only `.gitkeep`, and no Observer runtime exists.

```text
RUNTIME → evidence / proposal path → governed promotion → CANONICAL
never:
RUNTIME → automatic CANONICAL
```

**Contextual Knowledge is RUNTIME.** Knowledge held in Shared Runtime State ([`knowledge-experience.md`](knowledge-experience.md)) is contextual RUNTIME information in this architecture. No canonical Knowledge Kind exists or is created. This model avoids the ambiguous phrase "canonical knowledge": canonical definitions are system source, and contextual Knowledge belongs to Shared Runtime.

### RESEARCH

Includes external source research, target capability studies, upstream source inspection, frozen probe reports, comparative investigations, and license/provenance records (`research/`, `docs/research/`, `third-party/`).

```text
RESEARCH → analysis → proposal → evaluation → review → approval → adaptation → CANONICAL
never:
external repository → copy → CANONICAL
```

An external repository is a research source. By default it is never a runtime dependency or a wholesale import ([`docs/research/methodology.md`](../research/methodology.md)). External material may influence canonical source only after license review, provenance preservation, utility assessment, overlap assessment and an architectural-compatibility assessment. When a concept is adapted, record where applicable: source, license, what was adapted, what was not copied, and the Nexo-specific transformation.

**Research evidence != runtime authority.** A research record may inform architecture. It never controls execution by itself.

The research evidence notations in use (for example `DOC`, `SOURCE`, `RELEASE`, `OBSERVED_LOCAL`, `RELEASE_PINNED_SOURCE`, `DOCUMENTED / VERSION UNCLEAR`, `INFERENCE`, `NOT ESTABLISHED`, `UNKNOWN`) classify evidence inside RESEARCH. They are not information classes, and they are preserved exactly as written in `research/codex/`.

### GENERATED

The principal example is `dist/` (git-ignored and currently absent). The class also covers generated target files, generated distribution manifests (even when they carry provenance), and any future automatically generated documentation, even Markdown.

```text
GENERATED != SOURCE
```

- `dist/` is never edited manually and is never authoring input.
- Canonical meaning is never reconstructed by reading generated output as a primary source.
- Generated output may be inspected as evidence during Validation. Inspection does not change its class.
- Adapter output is never a source input for another adapter ([`docs/schema-system.md`](../schema-system.md)).

### VALIDATION

Includes tests, fixtures, Evaluation Runs, probe execution evidence, validation diagnostics, certification evidence and packages, and regression results.

- `tests/`, including `tests/fixtures/`, is VALIDATION even though it is source-controlled. **Source-controlled != automatically CANONICAL.** The schema fixture `tests/fixtures/schemas/valid/agent.json` (`context-agent`), for example, is validation evidence, not a published Agent.
- **Validation informs decisions. It does not promote.** A test `PASS` never rewrites source.
- **VALIDATION → Certification** is allowed when the claim, scope, evidence and freshness are sufficient ([`assurance-certification.md`](assurance-certification.md)). A certification decision may authorize a release gate according to Governance, but **VALIDATION evidence != CANONICAL definition**.

## What an information class is not

An information class describes **semantic role and authority**. It is independent of every axis below, and none of them may be inferred from another.

| Axis | Example values | Owner | Relationship to information class |
|---|---|---|---|
| Git tracking / mutability | tracked, ignored | Git | `tests/` is tracked and VALIDATION; `dist/` is ignored and GENERATED |
| File extension | `.md`, `.yaml`, `.json` | — | `.md`, `.yaml` and `.json` never imply CANONICAL |
| Entity lifecycle | `draft`, `experimental`, `stable`, `deprecated` | `common.schema.json` (`entityStatus`) | CANONICAL + `draft` and CANONICAL + `stable` are both CANONICAL |
| Completion status | `READY`, `PASS`, `FAIL`, `BLOCKED`, `INCOMPLETE`, `ESCALATION_REQUIRED` | `common.schema.json` (`completionStatus`) | a `PASS` Contract Instance remains RUNTIME |
| Observation result | `observed`, `validated`, `failed`, `blocked` | `observation.schema.json` | RUNTIME + `observed`; a `validated` Observation remains RUNTIME |
| Evidence class | `E0`–`E4` | `core/policies/evidence.md` | a RESEARCH record may contain E3 evidence; a VALIDATION artifact may contain E2 evidence |
| Enforcement level | `L1`–`L3` | `docs/concepts/enforcement.md` | unrelated to class |
| Research state | `FROZEN`, `INVALID` | research records | RESEARCH + `FROZEN` |
| Document authority class | `NORMATIVE`, `TECHNICAL_NORMATIVE`, `EXPLANATORY`, `DECISION`, `REVIEW`, `RESEARCH`, `STATUS` | [R1 audit](../reviews/r1-documentation-authority-audit.md) | classifies documents by authority, a separate axis |

```text
INFORMATION CLASS != LIFECYCLE STATUS
```

`metadata.status` is never used to infer information class: `stable` does not mean canonical, and `draft` does not mean non-canonical.

## Location helps classify; semantics and governance define authority

A directory supplies a **default** information class. Some content needs more precise classification. Authority depends on root, information class, schema/contract and governance, never on proximity:

- A file inside this repository does not become canonical by being in the repository.
- A file does not become canonical through its extension.
- A document does not become a canonical instance by using the canonical envelope or a registered `kind`.

| Location | Default class | Canonical authoring root? | Notes |
|---|---|---|---|
| `core/directives/`, `core/policies/`, `core/contracts/` | CANONICAL (semantic) | yes | Directive, Policy and Contract Definition |
| `core/schemas/` | CANONICAL (semantic) | no | loaded through `registry.json` by the schema loader; not discovered as entities |
| `agents/`, `skills/`, `rules/`, `workflows/`, `capabilities/`, `profiles/`, `enforcement/` | CANONICAL (semantic) | yes | placeholder-only today |
| `evals/` | CANONICAL (semantic) | yes | Evaluation **Definitions** only. Evaluation Runs are VALIDATION and do not belong here |
| `adapters/` | CANONICAL (target implementation) | no | authoritative implementation of one translation boundary; target-specific |
| `observer/` | RUNTIME | no | runtime evidence storage; `.gitkeep` only |
| `installer/` | RUNTIME / GENERATED boundary | no | its future source code may be authoritative implementation code; installed state and inventories are RUNTIME |
| `research/`, `docs/research/` | RESEARCH | no | probe records may contain runtime-derived evidence without becoming canonical input |
| `third-party/` | RESEARCH (provenance boundary) | no | never a runtime dependency by default |
| `dist/` | GENERATED | no | manual edits forbidden |
| `tests/` | VALIDATION | no | includes fixtures |
| `tools/` | VALIDATION (validation and phase-certification tooling) | no | implements checks; does not define canonical semantics |
| `docs/*.md` (top level) | CANONICAL (architecture and technical documentation) | no | owners of their technical topics; not entity instances |
| `docs/model/` | CANONICAL (organizational/system documentation) | no | NORMATIVE for organizational/system framing; not canonical machine authoring input |
| `docs/concepts/` | CANONICAL (technical semantic documentation) | no | technical Kind semantics; not entity instances |
| `docs/decisions/` | CANONICAL (governance/history documentation) | no | historical architectural authority; a historical state is not a current entity definition |
| `docs/reviews/` | VALIDATION (governance evidence) | no | classified by content; never a behavior source |
| `docs/adapters/` | by content | no | target design documents (for example the translation contract) document target implementation; capability summaries are RESEARCH; status trackers report evidence, and a **status claim != canonical target behavior** |
| root `AGENTS.md` | repository development guidance | no | governs agents developing this repository; never the product's canonical runtime directive (`core/directives/core-directive.md`) |

Repository development guidance sits outside the product information model. It is guidance for developing the repository, not a sixth class.

## Probe evidence: raw execution versus frozen record

```text
raw probe execution and its temporary artifacts   → RUNTIME / VALIDATION evidence
promoted, frozen research record summarizing it   → RESEARCH, with provenance to the raw evidence
```

The F2 attempt illustrates the split:

```text
%TEMP%\nexo-c4c-r5-f2-<timestamp>\ raw evidence
→ RUNTIME / VALIDATION evidence (outside the repository; not guaranteed to persist)

research/codex/probes/c4c-runtime-r5-f2-0.160.0.md
→ RESEARCH record (overall verdict INVALID, research state FROZEN),
  with SHA-256 provenance to the raw artifacts
```

The [frozen record](../../research/codex/probes/c4c-runtime-r5-f2-0.160.0.md) does not become canonical behavior. Its bounded observations, such as `agent.wait` → Codex internal `wait`, stay scoped to their Codex CLI 0.160.0 evidence ([`capability-runtime.md`](capability-runtime.md)). A RESEARCH record may contain runtime-derived E3 evidence without changing its class.

### Observation

```text
Observation schema    → CANONICAL technical contract
Observation instance  → RUNTIME evidence
OBSERVATION INSTANCE != CANONICAL BEHAVIOR
```

An Observation uses the canonical envelope (`apiVersion`, `kind: Observation`, `metadata`, `spec`). That does not make it canonical source. Its instances have no canonical authoring root, and `observer/` is not added to canonical discovery. An Observation may reference canonical entities through `spec.workflowRef`, `spec.execution.agentRefs` and `spec.subject`; it does not need to be in the canonical index to do so. `resultStatus: validated` is an Observation result, not a canonical status. The schema rejects `promoted` as a result status, as the fixture `tests/fixtures/schemas/invalid/observation-invalid-result-status.json` checks.

### ImprovementProposal

```text
ImprovementProposal schema    → CANONICAL technical contract
ImprovementProposal instance  → RUNTIME (governed evolution artifact)
IMPROVEMENT PROPOSAL != APPROVED CHANGE
```

`requiresExplicitApproval: true` is a schema constant (the invalid fixture with `false` is rejected). It states that approval is required, never that approval occurred. An ImprovementProposal is therefore not an approved change, not a Candidate promotion, and not canonical. "Governed evolution artifact" describes a kind of RUNTIME information; it is not a sixth `PROPOSAL` class.

- **What is promoted.** A proposal never becomes the final canonical behavior itself. It describes and motivates a governed change lifecycle. What is eventually promoted is the **approved Candidate/change**, applied to the appropriate canonical source. Moving or copying a proposal file into a canonical root is not promotion.
- **Attached material keeps its own class.** Evaluation evidence attached to or referenced by a proposal may be VALIDATION while the proposal instance stays RUNTIME. An artifact may reference information of another class without changing the class of either.
- **Physical location deferred.** This model decides no storage root for ImprovementProposal instances; that is deferred to implementation. No `proposals/` directory is created.

### Contract and Evaluation

```text
Contract Definition    → CANONICAL      Contract Instance → RUNTIME
Evaluation Definition  → CANONICAL      Evaluation Run    → VALIDATION
```

One Kind, `Contract`, defines the shape. Its runtime instance fills that shape and carries an actual completion status ([`docs/concepts/contracts.md`](../concepts/contracts.md)). One Kind, `Evaluation`, defines a check. Running that check produces validation evidence ([`assurance-certification.md`](assurance-certification.md)). No `Run` Kind exists. No production Evaluation Definition exists today; `evals/` holds only `.gitkeep`.

### Profile, Agent and Capability

- **Profile:** a Profile Definition is CANONICAL once a real entity exists (none does; the fixture `core-profile` is VALIDATION). The Effective Configuration derived from Profiles and configuration layers is RUNTIME ([`profiles-context-configuration.md`](profiles-context-configuration.md)).
- **Agent:** an Agent Definition is CANONICAL. A target role/config artifact rendered by an adapter is GENERATED (ADR 0005 previews remain non-deployable). A live child actor or session, such as the spawned child identified in the F2 record, is RUNTIME ([`workforce.md`](workforce.md)).
- **Capability:** a Capability Definition is CANONICAL. A Capability Binding is RUNTIME / target state. A target research matrix is RESEARCH ([`capability-runtime.md`](capability-runtime.md)).

### Candidate

A Candidate is a state/role of a change and is non-canonical ([`learning-evolution.md`](learning-evolution.md)). It is not an information class. Depending on mechanism, it may exist as a runtime artifact, a validation artifact or a temporary implementation branch.

## Identity

- **Canonical identity:** `Kind:id`, optionally `Kind:id@version` (ADR 0001, [`docs/canonical-format.md`](../canonical-format.md)). Each logical key is unique in the canonical index.
- **Runtime identity:** runtime artifacts may need identity or correlation, such as an Assignment id, cycle id, task id, Contract Instance id, Observation id or a target's child/session id. **Runtime identity != canonical identity.** No universal runtime ID schema is designed here. Observation and ImprovementProposal instances reuse the envelope's `metadata.id` syntax today, but a `Kind:id` built from it does not resolve in the canonical index.
- **Generated identity:** a generated artifact should be traceable to its source refs, source revision and adapter/target, where applicable. It does not need to become a canonical entity.

## Provenance

Provenance is the traceable origin and transformation history needed to understand where information came from and under what terms it may be used.

| Class | Provenance should preserve, where applicable |
|---|---|
| CANONICAL (external-derived) | source, license, attribution, adaptation history (`metadata.provenanceRefs` is optional; provenance graph resolution is deferred, per [`docs/schema-system.md`](../schema-system.md)) |
| RESEARCH | source, date/version, evidence classification, license/provenance, observation method |
| GENERATED | canonical source refs, adapter, generation version/revision |
| RUNTIME | execution, source, target/version, time/recency |
| VALIDATION | what was tested, against which revision, with which command/method, with which result |

```text
PROVENANCE != AUTHORITY
```

Knowing where information came from does not make it normative.

## Information flows

```text
CANONICAL
   ↓
ADAPTER
   ↓
GENERATED
   ↓
INSTALLER / TARGET
   ↓
RUNTIME
   ↓
OBSERVATION / EXPERIENCE
   ↓
LEARNING / EVOLUTION
   ↓
IMPROVEMENT PROPOSAL
   ↓
CANDIDATE
   ↓
VALIDATION / REVIEW
   ↓
APPROVAL
   ↓
PROMOTION
   └────────────→ CANONICAL

RESEARCH
   ↓
PROPOSAL / DESIGN INPUT
   ↓
same governed change path
```

| Transition | Status | Condition |
|---|---|---|
| CANONICAL → GENERATED | allowed | through an adapter or build step |
| GENERATED → target RUNTIME | allowed | through installer/reconciliation, under Governance (no installer is implemented) |
| RUNTIME → Observation → Experience | allowed | structured signals only ([`docs/concepts/task-observer.md`](../concepts/task-observer.md)) |
| RUNTIME / RESEARCH / VALIDATION → evidence for a proposal | allowed | as evidence only |
| VALIDATION → Certification | allowed | claim, scope, evidence and freshness are sufficient |
| GENERATED → VALIDATION (inspection) | allowed | the artifact stays GENERATED |
| RUNTIME → CANONICAL directly | **forbidden** | must pass the improvement lifecycle |
| RESEARCH → CANONICAL directly | **forbidden** | must pass analysis, proposal, evaluation, review, approval and adaptation/promotion |
| GENERATED → CANONICAL directly | **forbidden** | generated output is never reverse-engineered into authoritative source |
| VALIDATION → CANONICAL directly | **forbidden** | a `PASS` informs a decision; it never rewrites source |

**No direct feedback shortcut.** RUNTIME, RESEARCH, GENERATED and VALIDATION information never reaches CANONICAL without Governance.

### Proposal flow (condensed)

```text
Observation → Experience → Diagnosis → Hypothesis → ImprovementProposal → Candidate
→ Evaluation → Review → Approval → Promotion → Canonical
```

This condensed view follows information classes; it removes no gate. Aggregation and pattern detection, baseline and regression comparison, independent review and explicit approval remain exactly as defined by the master lifecycle in [`learning-evolution.md`](learning-evolution.md) and by `core/policies/self-improvement.md`.

## Promotion and history

- **Promotion turns an approved change into modifications of the appropriate canonical source.** It never converts an arbitrary runtime artifact into a canonical entity.
- **Promotion preserves history.** After promotion, the Proposal, Evaluation Runs, Review records and approval evidence remain historical evidence. Promoting the change does not erase them, even conceptually (the append-oriented principle in [`knowledge-experience.md`](knowledge-experience.md)).
- **Promotion changes canonical revision/state**, and depending on scope it may require a new entity version. No new versioning rule is designed here ([`docs/versioning.md`](../versioning.md)).

## Kind creation gate

```text
NEW NOUN != NEW KIND
NEW KIND != NEW CANONICAL ROOT
```

New concepts should not become Kinds merely because naming them is convenient. Before a new Kind is registered, an explicit decision must demonstrate at least:

1. stable semantics;
2. independent conceptual identity;
3. repeatable instances;
4. schema-validation value;
5. meaningful references/relationships;
6. a defined lifecycle and ownership;
7. a defined information class for its instances;
8. harness neutrality where required.

Guiding questions:

- **Independent identity.** If the concept exists only as a field, relationship, state, temporary responsibility or runtime correlation, prefer not to create a Kind.
- **Schema value.** *What real invalid state becomes detectable by giving this concept its own schema?* If the answer is vague, do not create the Kind yet.
- **Reference value.** *Do other entities need to address this concept independently and stably?* If not, a field or relationship may be enough.
- **Lifecycle value.** A Kind needs a meaningful lifecycle. The existence of generic metadata infrastructure is not a reason to create one.
- **Class before root.** Decide *what class its instances belong to* before deciding *which directory holds them*.

Registering a schema Kind and adding a canonical authoring root are **two separate decisions**, and neither implies the other. Observation and ImprovementProposal prove the distinction: both are registered Kinds, and neither has a canonical authoring root.

## Canonical root gate

Adding a canonical authoring root requires demonstrating that:

1. its instances define intended, governed system state;
2. manual, source-controlled authoring is appropriate;
3. canonical integrity indexing is required;
4. its references must resolve against the canonical index;
5. generated or runtime evidence is not being mistaken for source.

`CANONICAL_ROOTS` stays exactly as it is. `observer/`, `research/` and any future proposal location are not canonical roots.

## Runtime artifact gate

Not every runtime artifact needs a Kind. An internal interface, a log/event shape, a Contract Instance or a structured result may be enough.

## Directory restraint

No top-level directory is created merely because a conceptual noun exists. This model creates no `canonical/` wrapper (current canonical roots stay where they are), no `proposals/`, no `runtime/` (`tests/architecture.test.ts` asserts its absence), no `knowledge/` and no `validation/` directory. Tests and evidence are not reorganized.

## Validation layers and their scope

These layers remain separate, and none substitutes for another ([`docs/validation.md`](../validation.md), [`assurance-certification.md`](assurance-certification.md)):

| Layer | Implementation | Scope today |
|---|---|---|
| Schema validation | `tools/validate/schemas.ts` (`validate:schemas`) | compiles the 13 registered schemas; validates one valid and one invalid fixture per Kind, including the Observation and ImprovementProposal fixtures |

## Investigation results

### A. Observation `metadata.status`: CLARIFICATION (R2/R3)

- `common.schema.json` defines a single `metadata` shared by all 13 registered schemas, so every Observation must carry `metadata.status` (`draft`, `experimental`, `stable` or `deprecated`).
- History: Observation and ImprovementProposal were created in `e953831` with the shared metadata, which then required only `id`, `title` and `version`. `e706db3` ("fix(schema): align canonical model invariants") added the required `status` (`entityStatus`) to that shared definition for every Kind at once, alongside the `docs/canonical-format.md` text that calls it "the entity lifecycle". No commit, document, test or fixture assigns it a distinct meaning for runtime instances.
- Fixtures: the valid and invalid Observation fixtures use only `status: draft`. The lifecycle test ("entity lifecycle status is required and separate from completion status") exercises only a Directive fixture.
- Observation has its own result vocabulary (`spec.resultStatus`), whose enum excludes `promoted`.

Conclusion: the field exists because of the shared envelope; no runtime Observation lifecycle was designed for it. Its meaning for instances is **not established**. Until R2/R3 decides, it carries no semantics beyond schema conformance and must never be read as information class, canonical truth, validation outcome or promotion (`stable Observation != canonical truth`). The schema is unchanged.

### B. ImprovementProposal `metadata.status`: CLARIFICATION (R2/R3)

The envelope evidence above applies equally. In addition, the proposal schema has no decision or approval state field, and `requiresExplicitApproval` is the constant `true`. Approval, rejection and promotion state are therefore not representable in the schema today; the Candidate lifecycle vocabulary in [`learning-evolution.md`](learning-evolution.md) is conceptual. `metadata.status: stable` never means approved or promoted (`STABLE METADATA != CANONICAL PROMOTION`). R2/R3 must decide where proposal decision state lives and what `metadata.status` means for proposal instances. The schema is unchanged.

### C. Runtime reference validation: IMPLEMENTATION DEFERRED

- `tools/validate/references.ts` declares typed reference rules for Observation (`/spec/workflowRef` → Workflow, `/spec/execution/agentRefs/*` → Agent, `/spec/subject` → any) and for ImprovementProposal (`/spec/observationRefs/*` → Observation, `/spec/target` → any).
- `canonical-integrity.ts` applies those rules only to records in the canonical index, which holds only entities discovered under `CANONICAL_ROOTS` with a matching kind. No root has kind Observation or ImprovementProposal, so no current code path resolves the references of a real runtime instance. Schema validation checks only reference syntax (the `entityRef` pattern) in fixtures.
- By code inspection only (no test covers it): a canonical entity whose open (`ANY`) reference field pointed to an `Observation:` or `ImprovementProposal:` key would be reported as `UNRESOLVED_REFERENCE`, because such records never enter the index.

No mechanism exists today to resolve runtime artifact references, and a future one must not be assumed to work like the canonical index. `canonical-integrity.ts` resolves canonical authored references; it is not evidence that runtime references have a resolver. **IMPLEMENTATION DEFERRED.** No validator is created here, and no classification changes as a result.

### D. `requiredCanonicalDirectories`: CLARIFICATION (naming debt)

`tools/validate/repository.ts` exports `requiredCanonicalDirectories` (20 entries). It is used for two things: a required-directory presence check, and rejecting a nested `dist/` under each entry. Besides the canonical roots, it lists `core`, `core/schemas`, `observer`, `adapters`, `installer`, `tools`, `research`, `third-party` and `tests`. Repository shape requires these directories, but they are not canonical authoring roots: `observer/` is RUNTIME, `tests/` is VALIDATION and `research/` is RESEARCH. The list actually holds required repository directories, so its name is misleading. **Required repository directory != canonical authoring root.** This is naming debt only; behavior is correct. The code is unchanged, and the finding is recorded for R2/R3.
