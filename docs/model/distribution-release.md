# NexoHarness Distribution, Installation & Release

Status: ACTIVE. This document defines the organizational/system boundary from target-specific generation through installation, verification, certification, and product publication. It does not implement a Codex installer or replace the technical authorities for source ownership, Codex translation, accepted decisions, or tag mechanics:

```text
docs/source-of-truth.md
docs/versioning.md
docs/adapters/codex.md
docs/adapters/codex-translation-contract.md
docs/decisions/0005-codex-agent-role-rendering.md
docs/model/canonical-information.md
docs/model/profiles-context-configuration.md
docs/model/capability-runtime.md
docs/model/governance-authority.md
docs/model/assurance-certification.md
```

No Kind, schema, registry entry, canonical root, installer, uninstaller, doctor, filesystem distribution, package publisher, or target runtime behavior is introduced here. The accepted ADRs remain historical decisions; this model reconciles current system boundaries and does not amend them.

> **Adapters generate. Installers reconcile. Doctors inspect. Runtime verification proves target behavior. Certification establishes scoped assurance. Release publishes only eligible, approved output.**

## End-to-end boundary

```text
CANONICAL
  ↓
ADAPTER / COMPILATION
  ↓
RENDER
  ↓
GENERATED DISTRIBUTION
  ↓
MANIFEST
  ↓
INSTALLER RECONCILIATION
  ↓
TARGET
  ↓
DOCTOR
  ↓
RUNTIME VERIFICATION
  ↓
CERTIFICATION
  ↓
PRODUCT RELEASE
```

These are separate responsibilities and information states. A successful earlier step does not prove a later one succeeded. In particular:

```text
RENDERABLE != USABLE
RENDERABLE != DEPLOYABLE
TESTABLE != DEPLOYABLE
DEPLOYABLE != RELEASED
INSTALLATION != RUNTIME VERIFICATION
CERTIFICATION != RELEASE
```

## Distribution

A **Distribution** is a generated, target-scoped package of artifacts and metadata derived from an approved Nexo source selection for later installation. It is **GENERATED**, not canonical, runtime state, or a new registered entity.

A **Distribution Bundle** is the conceptual grouping of generated artifacts, manifest, provenance, hashes, diagnostics, and target metadata. It is not a new Kind. No `Distribution` schema or canonical authoring root is warranted by the existence of a package; `dist/` remains generated output and must never become source input.

```text
ADAPTER      → source-controlled, target-specific translation implementation
DISTRIBUTION → generated result of a governed selection and translation
```

An adapter owns mapping and rendering. A distribution records their result. A distribution may be used as a test fixture, candidate, preview, or certification input without becoming a product release. Its existence does not mean any target has been changed:

```text
DISTRIBUTION EXISTS != TARGET IS INSTALLED
```

### Renderability and deployment eligibility

Rendering establishes that target-native bytes can be represented. It does not establish that the compilation preserves every required semantic or authority boundary. ADR 0005 preserves this distinction:

```text
deploymentEligible = compilation.usable
                 AND renderer succeeded
                 AND no renderer-level blocking diagnostics
```

Artifacts rendered from an unusable compilation are **preview-only and non-deployable**. They may support bounded serialization, determinism, target-schema, or isolated runtime tests, but must never enter normal installation. Testing preview bytes does not promote them to deployable output.

The current Agent-role renderer exposes `deploymentEligible`; the current `CodexManifest` does not. Until that representation is resolved, **no Phase 1.2 consumer or installer may trust the manifest alone**. This is an implementation blocker before a Phase 1.2 manifest consumer. R1-M records the blocker; it does not change `adapters/codex/manifest.ts`. A later phase may choose the technical representation if that requires an API or schema decision.

### Deterministic, offline generation

For identical canonical selections, source versions, adapter version, target baseline, and explicit target configuration, the generated bytes must be identical. Generation must not depend on live filesystem discovery, a logged-in user, provider health, network access, the current clock, random identifiers, locale-dependent ordering, or machine-specific paths unless a governed future contract makes such a value an explicit input.

The generated target files and manifest use stable ordering, declared encoding and line endings, and content hashes. Runtime availability and target state belong to later inspection/reconciliation; they must not silently alter compiled bytes. These are distribution invariants, not a claim that a filesystem bundle is already produced.

## Manifest

A **Manifest** is generated metadata describing a distribution's identity, provenance, content hashes, target, runtime dependencies, diagnostics, and eligibility when that eligibility is represented. A manifest is **GENERATED**, not a canonical entity or an authorization decision.

The current Codex manifest contains exactly:

```text
manifestVersion
encoding
adapter
target
sourceRefs
runtimeDependencies
artifacts
diagnostics
```

It records adapter identity/version; target surface/version/tag; canonical source references; runtime dependencies; artifact paths and SHA-256 content hashes; and compilation diagnostics. It does not currently contain `deploymentEligible` or an explicit source-revision field. Do not describe either as an existing field.

SHA-256 content hashes support integrity checking:

```text
HASH != AUTHENTICITY
HASH != AUTHORIZATION
HASH != CERTIFICATION
```

A matching hash shows that bytes match the recorded digest; it does not establish who produced or approved them, whether the target will load them, or whether behavior is certified. Provenance and integrity do not manufacture authority.

## Installation and reconciliation

An **Installer** is the component responsible for reconciling an eligible generated distribution with an actual target environment. It consumes an eligible distribution and manifest, an explicit target installation scope, existing target state, ownership information, and applicable user/governance authorization. It does not redefine the canonical intent or repair the adapter's semantics.

Conceptual outputs may include a reconciliation plan, applied changes, preserved files, collisions, diagnostics, an installation inventory, and a verification result. These are design concepts only; no output schema is created.

The installer must not:

- modify canonical intent or silently rewrite generated semantics;
- turn a non-deployable preview into a normal deployment;
- widen Authority, grant Permission, or enable a Provider without authorization;
- overwrite a target file whose ownership is unknown or whose collision is unresolved;
- claim successful installation before checking the scoped target state.

The adapter never installs, merges, or overwrites target files. Existing Codex design requires a user-file collision to be reported, existing bytes to be preserved, and reconciliation to stop for explicit handling. Unknown ownership means **do not overwrite**. Drift detection does not itself authorize a mutation.

### Installation scope

An installation operation must name its target and installation scope explicitly and obtain authorization for that scope. Scope is an input to reconciliation, not something inferred from the current working directory, the logged-in user, or a discovered machine path. The current design material establishes the need for an explicit scope but does not define a scope taxonomy or Codex path-selection implementation. Those details remain for Phase 1.2.

Installation and removal are separate operations. The repository has no installer or uninstaller implementation; removal ownership and rollback mechanics remain unimplemented and must be designed before claiming them.

## Doctor and target verification

A **Doctor** inspects the installed target state and reports relevant presence, ownership, drift, collisions, diagnostics, and compatibility evidence. Inspection is distinct from reconciliation: a doctor does not silently repair state or grant authorization. No Doctor is implemented.

**Runtime verification** checks a claim against the actual target behavior and declared scope. Render success, a matching manifest hash, repository tests, mocks, or preflight checks alone do not prove that the target loaded or behaved according to the generated artifacts. Evidence must identify the target surface/version and other material platform, configuration, Profile, feature, and exclusion scope. If the claim requires target behavior, use target-runtime evidence or an explicitly justified equivalent.

Installation verification can show that expected changes were applied; it does not by itself prove runtime loading or behavior. A Doctor report is diagnostic evidence, not runtime certification.

## Certification and release

**Certification** is scoped assurance over specified claims, a revision, target, surface, version, configuration, and evidence. It may be required before product release, but it neither publishes artifacts nor changes their source. Certification of one revision, target, or Codex surface does not imply certification of another.

Phase certification tags and product versions remain distinct:

- `phase-<phase>-certified` identifies the exact approved repository SHA that passed fresh repository validation and the required independent review/approval gate. It certifies a phase revision; it does not assert Codex installation or runtime behavior.
- SemVer tags are reserved for actual distributable product versions. Product publication requires eligible output, applicable approval, and release validation; a passing repository workflow alone does not manufacture a product bundle or target certification.

The current `phase:close` command checks the approved SHA and synchronized clean `main`, runs fresh typecheck/validation/tests and whitespace validation, creates an annotated phase-certification tag, and pushes that tag. It does not build a Codex distribution, install artifacts, publish an npm package, or prove target runtime behavior.

The separate GitHub Release workflow accepts phase and SemVer tags (and manual dispatch for an existing tag), validates the tagged commit, then creates a GitHub Release with generated notes. It currently builds no Codex Distribution Bundle and uploads no product artifacts; npm and other external artifact publication remain absent. Thus a GitHub Release object attached to a certification tag is release automation output, not proof that Codex is packaged, installed, or certified.

Only eligible, approved output may be published as a product release. Release metadata must retain enough provenance to bind the released bytes to their source, adapter, target, hashes, approval, and applicable certification scope. Existing tag formats, immutability rules, and release classification remain owned by [`docs/versioning.md`](../versioning.md); this document does not change them.

## Current Codex implementation boundary

At the verified R1-M baseline, the Codex adapter compiles and renders artifacts **in memory only**. No filesystem Distribution Bundle is materialized; `dist/` is absent and remains generated output. The `installer/` directory contains only `.gitkeep`. Therefore:

```text
INSTALLER NOT IMPLEMENTED
UNINSTALLER NOT IMPLEMENTED
DOCTOR NOT IMPLEMENTED
FILESYSTEM DISTRIBUTION NOT IMPLEMENTED
TARGET RUNTIME CERTIFICATION NOT ESTABLISHED
```

The target-specific status and constraints are maintained in [`docs/adapters/codex.md`](../adapters/codex.md). The Codex translation contract owns mapping design; ADR 0005 owns the accepted Agent-role rendering and non-deployable preview decision. This model adds no contrary decision.

## R1-M blockers and non-goals

Before Phase 1.2 consumes a Codex manifest, the implementation must explicitly represent or otherwise safely resolve deployment eligibility; the consumer must not infer it from hashes or renderability. Phase 1.2 must separately establish explicit installation scopes, ownership-aware reconciliation, collision handling, and a safe verification/removal plan. A later target-runtime claim then needs suitable runtime evidence and independent assurance according to its scope.

R1-M is documentation reconciliation only. It does not modify adapter or release code, `CodexManifest`, schemas, Kinds, target files, or generated output; it does not create a package, implement an installer/doctor/uninstaller, or claim certification. The exact installation-scope taxonomy and eligibility representation remain implementation decisions.
