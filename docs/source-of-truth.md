# Source of Truth

NexoHarness has one canonical source. Harness-specific output is generated by adapters and is never maintained as a second manual implementation.

## Directory ownership

| Directory | Ownership | Classification | Canonical authoring root |
|---|---|---|---|
| `core/` | Foundational principles, schemas, contracts, directives and policies | CANONICAL | parent only; see its subdirectories |
| `core/directives/` | Canonical Directive definitions | CANONICAL | yes (Directive) |
| `core/policies/` | Canonical Policy definitions | CANONICAL | yes (Policy) |
| `core/contracts/` | Canonical Contract definitions | CANONICAL | yes (Contract) |
| `core/schemas/` | Schema registry and registered Kind schemas | CANONICAL | no; loaded through `registry.json`, not discovered as entities |
| `agents/` | Canonical agent behavior | CANONICAL | yes (Agent) |
| `skills/` | Reusable procedures | CANONICAL | yes (Skill) |
| `rules/` | Behavioral invariants | CANONICAL | yes (Rule) |
| `workflows/` | Coordination and state transitions | CANONICAL | yes (Workflow) |
| `capabilities/` | Abstract tool requirements | CANONICAL | yes (Capability) |
| `profiles/` | Capability bundles | CANONICAL | yes (Profile) |
| `enforcement/` | Runtime and structural protections | CANONICAL | yes (Enforcement) |
| `evals/` | Behavioral expectations and Evaluation Definitions (not Evaluation Runs) | CANONICAL | yes (Evaluation) |
| `observer/` | Runtime evidence and observation outputs | RUNTIME | no |
| Shared runtime state (conceptual; no directory reserved) | Scoped operational evidence and learned recommendations | RUNTIME | no |
| `adapters/` | Harness translation logic | CANONICAL implementation boundary (target-specific; not harness-neutral semantic source) | no |
| `research/` | External investigation and comparison | RESEARCH | no |
| `third-party/` | Provenance and license metadata | RESEARCH | no |
| `dist/` | Generated harness-native output | GENERATED | no |
| `installer/` | Future installation and verification tooling | RUNTIME / GENERATED boundary | no |
| `tests/` | Structural, integration and regression checks | VALIDATION | no |
| `tools/` | Validation and phase-certification tooling | VALIDATION | no |

Phase 0.0 through 0.2 create the directory shape and canonical definitions and validation foundation only. Empty canonical directories do not imply production behavior exists. The root `AGENTS.md` is repository development guidance; `core/directives/core-directive.md` is the product's canonical runtime directive. `observer/` is runtime evidence storage and is never a canonical authoring root.

The canonical authoring root column mirrors `CANONICAL_ROOTS` in `tools/validate/canonical-discovery.ts`, which lists 11 roots today. A directory required by repository validation is not thereby a canonical authoring root. `requiredCanonicalDirectories` in `tools/validate/repository.ts` also lists `observer`, `adapters`, `installer`, `tools`, `research`, `third-party` and `tests`, and that name is recorded naming debt: **required repository directory != canonical authoring root**.

## Registered Kinds and canonical authoring Kinds

`core/schemas/registry.json` registers **13 technical Kinds** today. **11** of them are canonical authoring Kinds: their instances are authored under a canonical root and discovered by canonical integrity validation. `Observation` and `ImprovementProposal` are registered Kinds without a canonical authoring root. Their schemas are canonical technical contracts, but their instances are RUNTIME artifacts: an Observation is runtime evidence, and an ImprovementProposal is a governed evolution artifact, not an approved change. Neither enters the canonical index. Using a registered `kind` and the canonical envelope does not make an instance canonical. Both counts describe current technical state, not permanent invariants; see [`docs/model/canonical-information.md`](model/canonical-information.md).

## Documentation layers

Architectural documentation is organized by what it governs, not only by directory:

| Layer | Owns | Root(s) |
|---|---|---|
| Organizational / system model | Why NexoHarness is shaped this way; cross-layer framing | `docs/model/` |
| Technical canonical Kind semantics | What each of the 13 registered technical Kinds means and how it behaves | `docs/concepts/` |
| Runtime evidence | Observed operational or probe results | `observer/`; frozen probe records under `research/*/probes/` are RESEARCH records summarizing runtime-derived evidence |
| Adapter implementation / status | A specific target's current implementation and constraints | `adapters/`, `docs/adapters/` |
| Generated artifacts | Derived, non-authoring output | `dist/` |
| Research | External or empirical investigation | `research/`, `docs/research/` |
| Historical decisions | What was decided and why, at the time | `docs/decisions/` |

`docs/model/` is organizational/system framing, not canonical authoring input; it is NORMATIVE for how the system is explained, not for schema-validated behavior. It cannot redefine a Kind, schema, Policy, or accepted ADR; see [`docs/model/README.md`](model/README.md) and the [R1 documentation authority audit](reviews/r1-documentation-authority-audit.md) for the reconciliation boundary.

## Definitions

NexoHarness uses exactly five information classes. A class describes semantic role and authority. It is not Git tracking, file extension or `metadata.status`. The full information model, including definition-versus-instance classification, is [`docs/model/canonical-information.md`](model/canonical-information.md).

- **CANONICAL** — authored source that defines intended behavior or its assurance requirements. It must remain harness-neutral where the architecture requires it.
- **GENERATED** — derived output produced by an adapter or build step. It must not be used as authoring input or edited manually.
- **RUNTIME** — evidence, execution or installation material used while the system operates. Runtime data cannot silently redefine canonical behavior.
- **RESEARCH** — external material used to inform design. Research is not a runtime dependency and requires provenance review before adaptation.
- **VALIDATION** — information whose primary purpose is to test, evaluate, verify or certify claims about another artifact or behavior, such as tests, fixtures, Evaluation Runs, validation diagnostics and certification evidence. Source-controlled validation material is not canonical source.

## Ownership rules

1. Canonical behavior is authored once.
2. Adapters may translate canonical definitions but may not redefine them.
3. Generated output may be deleted and regenerated from canonical inputs.
4. Observer evidence may produce proposals, never automatic promotion.
5. External sources remain research until license, provenance and evaluation requirements are satisfied.
6. Validation results inform governed decisions but never promote or rewrite canonical source.

## Learned runtime boundary

Canonical source describes intended behavior. Learned runtime state describes observed operational evidence and is not canonical. It may inform selection among already-authorized choices, but it cannot alter authority, weaken policy or become canonical authoring input by itself. Any canonical improvement must pass the proposal, evaluation, regression comparison, independent review, explicit approval and promotion lifecycle in `core/policies/self-improvement.md`.
