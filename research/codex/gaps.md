# Codex / Nexo Gap Analysis

Snapshot: 2026-10-05; selected research target is proposed local Codex CLI 0.160.0. See the [detailed matrix](capability-matrix.md) and [source provenance](sources.md). This records gaps for later phases; it does not solve them.

| Gap class | Gap / impact | Possible future strategy | Phase |
|---|---|---|---|
| **NO GAP** | Codex provides a useful local coding loop with repository inspection/editing, command execution, Git-visible work and read-only/workspace-write modes. Nexo can use the local CLI as a viable first target. | Verify and map exact capability effects; keep abstract Nexo names canonical. | 1.1 |
| **TRANSLATION GAP** | Codex `AGENTS.md` chain, override names, fallback behavior, cap and trust differ from Nexo precedence and scopes. Incorrect translation can lose or reorder canonical requirements. | Generate minimal, traceable instruction files; test nesting, byte limits, fallback, trust and conflicts. | 1.1 |
| **TRANSLATION GAP** | Codex `SKILL.md` and custom-agent TOML are native file formats, not Nexo Skill/Agent semantics. | Define explicit field mapping. Keep role and procedure separate; do not encode Nexo authority in either artifact. | 1.1 |
| **TRANSLATION GAP** | Codex native tool names/effects do not supply Nexo capability IDs or a profile-aware resolver. | Later adapter maps requests to audited local operations and reports missing/degraded capability; canonical core stays provider-neutral. | 1.1 |
| **ENFORCEMENT GAP** | Prompt instructions are advisory, and custom-agent role labels do not prevent unauthorized effects. | Pair generated context with least-privilege sandbox/approval config; test actual file, shell, network and alternate-tool paths. | 1.1 / 1.3 |
| **ENFORCEMENT GAP** | Codex permission policy does not map cleanly to Nexo `sourceModification`, `delegation`, `commandExecution`, `externalMutation`. Approval prompts are not the same as per-task authority. | Define conservative crosswalk, mark partial/impossible mappings, fail closed when the target cannot meet required effect boundaries. | 1.1 |
| **ENFORCEMENT GAP** | Experimental command rules have wrapper/tool coverage constraints; hook behavior includes event-specific non-blocking or unsupported responses. | Do not depend on experimental rules or hooks as sole critical controls. Re-verify maturity, test bypass paths and retain sandbox as primary boundary. | 1.1 |
| **RUNTIME GAP** | No first-class Nexo workflow state machine, typed handoff contract, gate, retry bound or bounded-remediation runtime was established. | Keep Nexo runtime responsible for state and validation. Translate procedural hints to Codex instructions/skills only as a secondary aid. | 2.x / 3.x |
| **RUNTIME GAP** | Shared Runtime scopes, project isolation, cross-harness state, confidence/staleness and canonical promotion are not equivalent to Codex conversation resume or local memories. | Define Nexo storage/privacy/lifecycle separately; treat Codex context as target session state only. | 5.x |
| **RUNTIME GAP** | `codex review` is not by itself Nexo E4 independent verification; approval auto-review assesses eligible action approvals, a different responsibility. | Nexo review workflow must establish separate reviewer context/identity, evidence, findings and independence criteria. | 3.x / 6.x |
| **TELEMETRY GAP** | Hooks, transcript paths and `codex exec --json` expose useful candidate events, but not a single stable, complete, normalized observer contract. Transcript format is explicitly not stable. | Future collector should use structured supported events, version-gated parsing and absent-value semantics; minimize prompt/source capture. | 5.0 / 5.1 |
| **TELEMETRY GAP** | Approval decisions, detailed durations, full subagent lifecycle and normalized workflow/capability identities may be unavailable or client-specific. | Verify each signal by event and surface; mark unavailable instead of inferring from text or fabricated telemetry. | 5.1 |
| **VERSION / MATURITY GAP** | `.rules` is explicitly experimental; app-server is experimental; current docs for hooks, agent config, memory and some security details are mutable/unpinned. | Pin stable CLI release; re-run capability/effect tests before implementing or certifying any dependent feature. Exclude experimental dependencies from V1 unless separately approved. | 1.1 / 1.3 / 6.x |
| **VERSION / MATURITY GAP** | IDE and desktop app share local configuration in part but have independent UI/client updates and additional behaviors. | Certify CLI first; maintain per-surface version/test rows before claiming parity. | Later parity |
| **VERSION / MATURITY GAP** | Windows sandbox behavior depends on Windows build, elevated setup, enterprise policy, native versus WSL, and fallback mode. | Declare supported Windows/WSL combinations and test their effective boundaries; show degraded status for unelevated fallback. | 1.1 / 1.2 / 1.3 |
| **UNKNOWN** | Exact feature-by-feature inclusion in CLI 0.160.0 is unclear where official docs do not pin version or changelog. | Inspect tag-pinned source/tests only for features Phase 1.1 will use; supplement with `OBSERVED_LOCAL` execution against the pinned binary. | Before 1.1 |
| **UNKNOWN** | Effective availability under all account types, managed restrictions, project trust states and user configuration combinations is not established. | Record test matrix by OS, auth, config/managed policy and trust state; never assume account rollout equals product-wide support. | 1.1 / 1.3 |
| **UNKNOWN** | Complete browser/computer-use/image capabilities available to the *local CLI target without MCP* are not established across accounts/platforms. | Avoid making these required V1 capabilities; verify only if a canonical capability requires them. | 1.1 |
| **UNKNOWN** | Whether every hook handler/event in current docs is present, stable and blocking-capable in release 0.160.0 is not established. | Pin docs/source/tests to release; test each intended hook and its failure behavior before any Observer/gate dependency. | Before 1.1 / 5.x |
| **VERSION / MATURITY GAP** | `model_instructions_file` appears in current configuration documentation/upstream main, but its presence and interaction with AGENTS.md in CLI 0.160.0 are not established. | Keep it out of the initial translation plan until tag-pinned evidence and a direct precedence test establish safe behavior. | Before 1.1 |

## Classification usage

`UNKNOWN` means evidence is insufficient, not that Codex lacks the feature. `UNSUPPORTED` should be used only after target evidence shows a requirement cannot be represented sufficiently. No phase 1.0 gap is being resolved by claiming equivalence to API, cloud, IDE or unreleased main behavior.
