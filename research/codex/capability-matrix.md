# Codex Capability Matrix — Detailed Evidence

Research date: **2026-10-05**. Stable baseline observed: **Codex CLI 0.160.0**, `rust-v0.160.0`, released 2026-10-01. Upstream `openai/codex` main separately observed at **`3f1ccb7ceb814e54314826f68d61c892e2f5a48e`** on 2026-10-05. Provenance and sources are in [sources.md](sources.md). `DOC` means official docs; `SOURCE` means official repo; `TEST` means pinned upstream test; `RELEASE` means official release evidence; `OBSERVED_LOCAL` means direct local execution. A current doc without an explicit version is not silently promoted to stable-release proof.

| **Codex Cloud / managed** | Remote Codex tasks and managed environments/configuration, including ChatGPT Work or cloud-executed coding work. | Out of scope for V1. Cloud owns remote environment/session behavior and managed-policy surfaces not equivalent to local CLI. Do not infer local behavior from it. |

The Codex CLI / local Codex harness is the accepted Phase 1.0 target decision following independent review. This document remains research and design input, not adapter implementation. V1 assumes users install supported Codex CLI 0.160.x or a later explicitly reverified release; it does not assume all clients, plans, operating systems or enterprise policies expose identical options.

## Controlled classifications

- **NATIVE** — the selected surface directly provides the required semantic behavior.
- **NATIVE_WITH_CONSTRAINTS** — behavior exists but has significant scope, policy, platform or maturity constraints.
- **ADAPTER_TRANSLATABLE** — later generated Codex-native instructions/config can express the requirement without a separate Nexo engine.
- **NEXO_RUNTIME_REQUIRED** — Codex alone does not own/guarantee the required Nexo behavior.
- **UNSUPPORTED** — current evidence demonstrates the target cannot represent the requirement sufficiently.
- **UNKNOWN** — evidence is insufficient or inconsistent.

Enforcement strength uses Nexo's distinctions: **HARD ENFORCEMENT** (OS/runtime boundary), **RUNTIME GATE** (Codex blocks or requests approval), **PROMPT / ADVISORY ONLY** (model-facing guidance), and **NONE/UNKNOWN**. Capability presence never implies authorization.

## High-value questions — findings

1. **Can root/core behavior be translated without manual duplication?** Yes, as generated project instructions is plausible (`ADAPTER_TRANSLATABLE`), but not as a dynamic canonical reference. Generated content must be traceable and budgeted; prose remains advisory.
2. **Does project precedence map cleanly to AGENTS inheritance?** Partially. Nested files and overrides provide layers, but closest-to-CWD concatenation is not a full authority/override engine and the byte limit can truncate.
3. **Do Nexo Skills map semantically to Codex Skills?** Partially. File format and progressive loading align, but a Codex skill is not a Nexo semantic entity or authority boundary.
4. **Do Nexo Agents map to custom agents without mixing role and authority?** The role/instruction portion maps; authority does not. Keep sandbox/approval policy separate.
5. **Can current subagent controls represent Nexo delegation policy?** Partially. Spawn, coordination and parent permission inheritance exist, but Nexo's required bounded contract and parent accountability are not structurally enforced.
6. **Can minimum sufficient orchestration avoid spawning for bounded work?** It can be instructed to; no structural guarantee/classifier was evidenced. This remains advisory unless Nexo controls path selection.
7. **Can Codex enforce read-only reviewer behavior strongly enough?** Sandbox read-only is strong for covered local execution; role wording alone is not. All tool/effect paths and Windows fallback must be tested.
8. **Can Codex enforce dimensional authority?** Not cleanly. Sandbox, network, approvals and command rules are coarse/orthogonal controls; Nexo's four authority dimensions need Nexo-side policy/mapping.
9. **Can independent review be represented?** `/review` documents a dedicated reviewer flow, and `review_model` can override the default model. Nexo must still verify reviewer context/config, independence and E4 evidence; these details are not pinned to 0.160.0.
10. **Which Observer signals are available without modifying Codex?** Candidate session, tool, compaction, subagent lifecycle and `exec` JSONL/usage events. Hooks and transcript stability/coverage constrain completeness; approval decisions and normalized metrics remain uncertain.
11. **Which Shared Runtime requirements remain Nexo-owned?** GLOBAL/WORKSTYLE/PROJECT/TASK scopes, isolation, portability, confidence/staleness, structured normalization, retention and canonical promotion.
12. **Which Nexo concepts lack a Codex-native equivalent?** Nexo authority dimensions, workflow state machines/contracts, capability resolver, shared cross-harness runtime, Observer schema and governed canonical promotion.
13. **Which features are too unstable to depend on for V1?** `.rules` is explicitly experimental; app-server is experimental; current-doc-only hook handler behavior and any main-only implementation are conditional until release-pinned. Stable CLI `exec`/`review` labels still require target release tests.

## Stable versus main

- **Stable release verified:** latest non-prerelease release observed was CLI 0.160.0 (`rust-v0.160.0`) on 2026-10-01 (S01/S02). This pins the baseline, not every feature row.
- **Main snapshot:** `3f1ccb7ceb814e54314826f68d61c892e2f5a48e` observed 2026-10-05 (S03). No feature is counted as stable merely because it appears in this commit.
- **Documented but version unclear:** AGENTS details, skills, custom agents, hook event semantics, Windows sandbox, local memories and many config keys unless the individual source explicitly says stable/experimental.
- **Explicit maturity:** current command reference marks `codex exec`, `codex review`, resume and core CLI commands Stable; marks app-server Experimental. Current config reference marks multi-agent collaboration Stable/on-by-default; rules documentation calls `.rules` experimental. Exact inclusion in 0.160.0 must be confirmed before implementation.
- **No unsupported claim:** absence from docs or this table is `UNKNOWN`, not proof of unsupported behavior.
