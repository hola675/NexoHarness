## 1. Objetivo y baseline

Este inventario examina selectivamente el código fuente del release fijado para contestar cuestiones que K2-P0 deja como `PENDING_DISCOVERY`. No cambia K1, K2-P0, el informe K2-P0-R2, la política de Governance ni el estado de K2-P1. Ningún hallazgo afirma cómo se comporta una extensión ya instalada en un equipo Windows.

El HEAD de NexoHarness se comprobó antes de trabajar y coincidía con el commit comunicado `2fb257e0b43b3b9b3852008ba06bc1737502523b`; el PR seguía en su rama separada. Se creó una rama propia de investigación a partir de ese SHA, sin modificar la rama del PR. El commit final de investigación queda registrado en el historial de esta rama.

Para upstream, `git ls-remote` confirmó que `refs/tags/v7.8.8` apunta a `e2887f08e5a6394299c810ba508f358aaf4c5bc3`; el objeto commit y los blobs referenciados también se verificaron. Toda consulta de código se hizo con ese SHA explícito (`git grep`, `git blame`, `git show`), no con `main`. No se ejecutó el cliente, sus pruebas o el código de Kilo. No se consultó documentación rolling como sustituto de la fuente del release.

## 3. Baseline interno comprobado

K1 §8 separa las obligaciones de precedencia, permisos, autonomía, límites del filesystem, discovery/reload y rutas/globs. K0 distingue `findingState` de `evidenceConfidence`, mantiene provider como cuestión separada de capability/permission y no contiene probes locales del target. ADR 0007 mantiene Windows + VS Code como target prioritario. La revisión histórica K2-P0-R y R2 concluyeron que el diseño es seguro como catálogo de gaps pero que F01/F02 bloquean readiness de ejecución reproducible.

El protocolo K2-P0 revisado ya especifica fixtures sintéticos, gate de invocación y estados bloqueados. Este inventario puede cerrar hechos estáticos (ID de tool, clave de permission, formas de regla, orden de algunos loaders), pero no rellena las observaciones que dependen de VS Code + Windows. El protocolo y el informe histórico se mantienen intactos.

## 5. S0-02 — Sintaxis y resolución de permisos

**Pregunta:** qué es una regla, cómo se selecciona, qué prevalece y cómo se puede aprobar/rechazar.
**Componentes:** `ConfigPermissionV1`, `Permission.fromConfig/evaluate/resolve/ask/reply`, `ReadPermission`, `ExternalDirectoryPermission`, `AgentManagerPermission`.
**Fuentes:** [`core/v1/config/permission.ts` L5-L56](https://github.com/Kilo-Org/kilocode/blob/e2887f08e5a6394299c810ba508f358aaf4c5bc3/packages/core/src/v1/config/permission.ts#L5-L56); [`permission/index.ts` L98-L135](https://github.com/Kilo-Org/kilocode/blob/e2887f08e5a6394299c810ba508f358aaf4c5bc3/packages/opencode/src/permission/index.ts#L98-L135), [L160-L270](https://github.com/Kilo-Org/kilocode/blob/e2887f08e5a6394299c810ba508f358aaf4c5bc3/packages/opencode/src/permission/index.ts#L160-L270), [L285-L365](https://github.com/Kilo-Org/kilocode/blob/e2887f08e5a6394299c810ba508f358aaf4c5bc3/packages/opencode/src/permission/index.ts#L285-L365), [L478-L525](https://github.com/Kilo-Org/kilocode/blob/e2887f08e5a6394299c810ba508f358aaf4c5bc3/packages/opencode/src/permission/index.ts#L478-L525).

### Forma de regla estáticamente confirmada

- `Action` acepta `"ask"`, `"allow"`, `"deny"` y `null`. `null` se usa como sentinel de borrado al combinar configuración; no es una cuarta decisión de ejecución.
- `Rule` puede ser una acción escalar (normalizada a patrón `"*"`) o un mapa de patrón a acción. `permission` admite claves conocidas explícitas y claves adicionales como strings (schema `StructWithRest`). En ejecución `fromConfig` expande cada patrón y aplana la configuración a `{permission, pattern, action}`.
- Entre las claves explícitas están `read`, `edit`, `glob`, `grep`, `list`, `bash`, `task`, `external_directory`, `markdown_source`, `todowrite`, `question`, `webfetch`, `websearch`, `lsp`, `doom_loop`, `skill`, `agent_manager`, `notebook_read`, `notebook_edit`, `notebook_execute`. La posibilidad de keys adicionales no prueba que una key arbitraria tenga un caller efectivo.
- `SCALAR_ONLY_PERMISSIONS` incluye `todowrite`, `todoread`, `question`, `webfetch`, `websearch`, `doom_loop`; otros permisos pueden tener patrones. El schema visible no transforma todos los campos en el mismo tipo.

### Dos niveles de orden diferentes

1. **Coincidencia de reglas dentro de un ruleset:** `Permission.evaluate(permission, pattern, ...rulesets)` aplana los arrays en el orden recibido y usa `findLast()` cuya regla coincide tanto con el nombre de permiso como con el patrón. Si nada coincide, devuelve `ask`. No ordena por “más específico” en esta función. Las propiedades conservan orden fuente porque el parser usa `propertyOrder: "original"`. Un operador no debe aplicar aquí la regla de orden de `Wildcard.all` utilizada por otros consumidores.
2. **Resolución del resultado base frente a approvals/overrides:** `Permission.resolve()` calcula una regla base (con hardening para `read`, `external_directory` y Agent Manager), calcula las reglas guardadas/sesión aparte y combina: una denegación base o guardada vence; si base es `ask`, sólo un `allow` guardado que cubra el patrón base lo sustituye; si base permite, un saved allow puede ser el resultado. `external_directory` usa un evaluador especializado. Esta prioridad de runtime no implica la prioridad entre archivos/capas de configuración.

### Aprobación interactiva y persistencia

`ctx.ask` puede crear una entrada pendiente con ID, sesión, permiso, patrones, `always`, metadata y deferred. La decisión `once` resuelve la llamada sin guardar una regla global; `always` guarda regla(s) global(es) mediante `config.updateGlobal` (salvo rutas/config protegidas que degradan el alcance). El código emite eventos de permiso preguntado/reply; los rechazos y denegaciones son errores/tipos distintos (`RejectedError`, `DeniedError`), no equivalentes a ausencia de llamada. `Permission.allowEverything` admite alcance sessionID o global; esta API no prueba que la UI exponga ambos ni qué control active. **Pregunta:** qué código realmente interpreta patrones/rutas y qué vector puede derivarse sin afirmar un Windows runtime result.
**Componentes:** permission `Wildcard`, shell structured pattern matching, `FSUtil`, `Glob`/`minimatch`.
**Fuentes:** [`util/wildcard.ts` L1-L45](https://github.com/Kilo-Org/kilocode/blob/e2887f08e5a6394299c810ba508f358aaf4c5bc3/packages/opencode/src/util/wildcard.ts#L1-L45), [`core/fs-util.ts` L145-L180](https://github.com/Kilo-Org/kilocode/blob/e2887f08e5a6394299c810ba508f358aaf4c5bc3/packages/core/src/fs-util.ts#L145-L180), [L215-L275](https://github.com/Kilo-Org/kilocode/blob/e2887f08e5a6394299c810ba508f358aaf4c5bc3/packages/core/src/fs-util.ts#L215-L275), [`core/util/glob.ts` L1-L34](https://github.com/Kilo-Org/kilocode/blob/e2887f08e5a6394299c810ba508f358aaf4c5bc3/packages/core/src/util/glob.ts#L1-L34), [`shell.ts` L325-L365](https://github.com/Kilo-Org/kilocode/blob/e2887f08e5a6394299c810ba508f358aaf4c5bc3/packages/opencode/src/tool/shell.ts#L325-L365).

1. **Permission wildcard** no es el `Glob` de archivos: reemplaza `\` por `/`, escapa regex especiales, `*` pasa a `.*`, `?` a `.`, ancla el regex al string entero y usa flags `si` en win32 (case-insensitive y dotAll) frente a `s` en otras plataformas. `*` puede abarcar separadores; no es `**` de fast-glob/minimatch con semántica usual de segmentos. El patrón especial que termina en ` .*` hace opcional la cola de comando.
2. `Wildcard.all` ordena patrones por longitud ascendente y luego lexicográficamente; el último match gana. `Wildcard.allStructured` aplica el mismo orden y compara head/tail de comandos. Esto aplica a ese matcher consumidor; `Permission.evaluate` independientemente conserva orden de ruleset y `findLast`.
3. File discovery `Glob` usa paquete `glob`, `globSync` y `minimatch` para coincidencia; `follow` depende de `symlink`. No se deben tratar estos patrones como el mismo dialecto que el regex de permission.
4. `FSUtil.normalizePath` en `packages/core/src/fs-util.ts` y `normalizePath` en `packages/opencode/src/util/filesystem.ts` hacen rama `win32`, resuelven el path Windows y consultan `realpathSync.native`; al fallar conservan el path resuelto. `normalizePathPattern` conserva `*` y, para un patrón de directorio terminado en `/*`, normaliza el directorio sin resolver el wildcard como path literal. `windowsPath` traduce formas `/C:/...`, `/c/...`, `/cygdrive/c/...` y `/mnt/c/...` a drive-letter Windows. Son dos helpers y callers distintos, no una garantía de que toda operación los use igual. Código fuente muestra ramas `process.platform === "win32"`; no prueba drive mapping, case-preservation efectivo del filesystem, Unicode normalization, junction resolution ni resultados del matcher en una instalación Windows.

Config `instructions` and URLs add separate sources. Exact loaded paths depend on working directory, trust, flags, and file existence.
- **Agents/modes:** each config dir is scanned for `{agent,agents}/**/*.md` (and mode variants), parsed with frontmatter. Variables `{env:}`/`{file:}` depend on `trusted` and file scope; untrusted project agent file reads are scoped. `mergeAgentMarkdown` combines definition fields; this is distinct from the global/project config merge and not proof of permission precedence by layer.
- **Commands:** `ConfigCommand.load(dir)` scans `{command,commands}/**/*.md`; file basename/frontmatter produce command IDs/templates. The source directory itself must be among loaded config dirs.
- **Kilo skills:** roots include home `~/.kilocode`, home `~/.kilo` (that order), VS Code global storage `%APPDATA%/Code/User/globalStorage/kilocode.kilo-code`, plus project/worktree `.kilocode` and `.kilo` directories scanned from the project path. The source comment states global paths load first and project paths last. Kilo config dirs match `{skill,skills}/**/SKILL.md`; separately, external Agent/Claude skill roots use `skills/**/SKILL.md`. Scanning carries trust provenance. Presence in a root is not evidence that a concrete extension install has the root or that a skill was presented to the model.
- **`kilo.jsonc`:** recognized among project config files with `kilo.json`, `opencode.jsonc`, `opencode.json`; global config supports the five filenames in §6. The source’s config-file root logic and extension’s working directory affect discovery. No install/merge behavior is inferred.
- **`.kilo/rules/`:** the inspected source loaders explicitly cover instruction files, config, agent/mode Markdown, commands and skills. They do not provide a verified separate `.kilo/rules/**` loader in those paths. Because this was a targeted loader inspection rather than a proof over every extension contribution, status is `UNKNOWN`, not `UNSUPPORTED`.
- **Reload:** global stamp checks can invalidate/reload global config on future access; project config/agent/commands are loaded in runtime instance state. No source evidence located in these paths establishes automatic in-session watch/reload for each project file or the exact VS Code user action that refreshes it. A fresh process/session is a candidate boundary; its observed effect remains `NEEDS_PROBE`.

## 13. R2-F01 preconditions

The upstream extension process architecture is known: VS Code starts the bundled Kilo CLI server locally and uses an SDK/loopback HTTP+SSE connection; that is transport/backend, not a model. The model provider request originates later in the session pipeline. Static source does not identify an approved credential-free provider/model that can deterministically emit the required calls through the extension UI. No mock provider, local model, test proxy, network route or credential was created/configured.

To remove F01 in a separate authorized gate, Governance would need to approve a provider/model setup and trust boundary (including egress and loopback exposure if applicable), and a plan must show that it returns a specific tool-call through the extension’s request, permission, execution and observable-result path. Otherwise runtime P01/P02/P04/P05-marker/P06 remain `BLOCKED`. This report does not recommend enabling external network or real credentials and does not make F01 pass.
